# 驗收測試：Roy 要跑的情境（001-core）

**格式**：照 spec-kit 的 quickstart.md（用真實操作驗證 spec）。
**目標**：Roy 不靠我們解釋，30 分鐘內跑完。每個情境對應 `spec.md` 的使用者情境和成功標準。
**規則**：只要哪一步卡住、看不懂、覺得麻煩，就跟自己的 agent 說一聲，它會記成一筆卡點紀錄（`notes/friction/`）。卡點紀錄比「通過」更有價值。

## 事前準備（小婕做）

1. 兩個人都照 plan.md 從 repo 安裝 `tandem`（001 階段還沒發布到 npm）。
2. **用小婕的個人 repo 測試**，例如新建 `jielle2453/tandem-trial`。原因：Roy 是 sudo-studio-lab 的擁有者，本來就能存取組織裡所有 repo，邀請流程測不出來；用個人 repo 也順便測到「個人 repo 加協作者」這種很多黑客松團隊的用法。
3. 在那個 repo 執行 `tandem`，確認看板打開。
4. 在看板上邀請 `theroyatlas`，把連結傳給 Roy。
5. 跟自己的 agent 做一個會影響 Roy 的決定，並開一個問 Roy 的問題。

## 情境 A：加入專案（對應情境 1、SC-001）

1. 打開小婕傳來的連結，照畫面做。
2. 開始計時，到看見看板為止。

**通過**：10 分鐘內看到看板；過程中沒有自己執行 git 指令，也沒有去收邀請信。
**記錄**：花了幾分鐘、哪一步最不確定。

## 情境 B：開工（對應情境 2、SC-003）

1. 在專案資料夾打開你平常用的 agent（Codex 或 Claude Code），隨便說一句話，例如「開工」。

**通過**：agent 第一個回覆就提到小婕的新決定和等你回答的問題，五行以內，有連結。
**再試一次**：關掉再開，同樣的事不應該再報告一次。

## 情境 C：回答問題（對應情境 4）

1. 照 agent 給的連結（或 GitHub 通知）打開那個問題，用自己的話回答。

**通過**：看板上「小婕在等 Roy」消失；小婕下次開工時，她的 agent 提到你回答了。

## 情境 D：做一個決定（對應情境 3、SC-004）

1. 跟你的 agent 討論一件跟 Tandem 有關、你真的有意見的事，最後做出決定。
2. agent 會給你看「我記成這樣，對嗎？」，檢查原話是不是你說的原句。

**通過**：原話一字不差；確認後小婕那邊開工時看得到；你沒有自己寫任何格式。

## 情境 E：只看看板（對應情境 5、SC-005）

只看看板，不問小婕，回答：

1. 小婕現在在做什麼？
2. 她在等誰、等什麼？
3. 她最近做出了什麼？點得開嗎？

**通過**：三題都答對（之後跟小婕對答案）。

## 情境 F：換一家 agent（對應 FR-007）

用另一家 agent（Codex 換 Claude Code，或反過來）重做情境 B。

**通過**：行為一樣。

## 測完之後

兩個人一起看 `notes/friction/` 和這份清單的結果，決定下一輪要改什麼，並把改動記成決定。
