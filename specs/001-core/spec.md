# 功能規格：Tandem 核心（001-core）

**狀態**：草稿
**建立**：2026-11-15
**格式**：照 GitHub spec-kit 的 spec 範本（使用者情境 → 需求 → 成功標準）。這份只寫「做什麼、為什麼」，不寫技術；技術在 `plan.md`。
**依據的決定**：D-20261115-0e4（輕鬆、邀請就能開始）、D-20261115-5f1（直接做完整版再調整）、D-20261115-8a2（先本機網頁）、D-20261115-3d9（照搬驗證過的做法）

## 這份要解決的問題

兩個人各自用自己的 AI agent 都做得很好，一起做卻常常在等：等對方做決定、等對方把想法整理成文件、等文件傳過來才發現少了東西（notes/friction/F-20261115-1a2、F-20261115-9b3）。之前試過寫一整套規則（studio），結果太麻煩沒人用（F-20261115-c4d）。

Tandem 核心要做到：**邀請隊友就能開始；每個人照常跟自己的 agent 工作，決定和狀態由 agent 記下來；誰都能隨時看到專案進展和每個人在做什麼。人不需要學任何規則。**

## 使用者情境與測試

### 情境 1：開始一個專案並邀請隊友（優先度 P1）

小婕在一個 GitHub repo 裡開始用 Tandem，輸入 Roy 的 GitHub 帳號邀請他，把分享連結傳給他。Roy 點開連結，照著畫面做完，就看到同一個專案的看板。

**為什麼是 P1**：這是「輕鬆」的第一關。studio 就是卡在一開始不知道怎麼做。
**獨立測試**：用兩個 GitHub 帳號，從零開始，不看任何文件，量兩個人都看到看板花多久。

**驗收情境**：
1. **假設** 小婕有一個 GitHub repo 和本機 clone，**當** 她執行一個指令開始使用 Tandem，**則** 專案需要的檔案和給 agent 的規則自動建好，並打開看板。
2. **假設** 小婕在看板上輸入 Roy 的 GitHub 帳號並按邀請，**當** 邀請送出，**則** 她拿到一個可以傳給 Roy 的連結。
3. **假設** Roy 收到連結，**當** 他打開並用 GitHub 登入，**則** 邀請自動被接受、專案下載到他電腦、看板打開，不需要他去收信或執行 git 指令。
4. **假設** repo 裡原本就有 AGENTS.md 或 CLAUDE.md，**當** 開始使用 Tandem，**則** 原有內容完全保留，Tandem 只加上自己的一段。

### 情境 2：開工時知道跟我有關的變動（優先度 P1）

Roy 隔天打開自己的 Codex。agent 一開始就用幾行話告訴他：小婕昨天做了兩個決定、其中一個影響他負責的部分、還有一個問題在等他回答。

**為什麼是 P1**：這是取代「傳一份長文件」的核心。
**獨立測試**：小婕記一個決定、開一個問 Roy 的問題；Roy 用 Claude Code 和 Codex 各開一次 session，看 agent 有沒有在第一個回覆就提到這兩件事。

**驗收情境**：
1. **假設** 上次之後有人新增了決定、問題或狀態變化，**當** 使用者開始一個 agent session，**則** agent 在第一個回覆用五行以內說出跟他有關的部分，並附上連結。
2. **假設** 上次之後沒有任何跟他有關的變動，**當** 他開始 session，**則** agent 不額外報告。
3. **假設** 同一批變動已經報告過，**當** 他再開一個 session，**則** 不重複報告。
4. **假設** 使用者用的是 Claude Code 或 Codex，**則** 兩者的行為一樣。

### 情境 3：記下決定，連同原話（優先度 P1）

小婕跟自己的 agent 討論後說「好，就用本機網頁先做」。agent 問她：「我記成這樣，對嗎？」並列出原話、決定、原因。她說對，決定就同步出去，Roy 下次開工就會知道。

**為什麼是 P1**：決定和原話是 agent 之間共享脈絡的主體。
**獨立測試**：在對話中做一個決定，檢查產生的紀錄有逐字原話、出處、強度，而且隊友看得到。

**驗收情境**：
1. **假設** 使用者在對話中做了一個會影響別人的決定，**當** agent 判斷值得記錄，**則** agent 先給使用者看紀錄內容，使用者確認後才同步。
2. **假設** 紀錄引用了**別人**的話，**當** 沒有附上那句話的出處連結，**則** 系統拒絕或把它標成「轉述」。
3. **假設** 新決定推翻了舊決定，**則** 新紀錄連到舊紀錄，舊紀錄標成「已取代」，兩筆都保留。
4. **假設** 兩個人同時各記一個決定，**則** 兩筆都成功同步，不會撞號、不會衝突。

### 情境 4：問隊友、意見不同（優先度 P2）

小婕的 agent 發現有件事需要 Roy 決定才能往下做，就開一個問題給 Roy。Roy 手機收到通知，用自己的話回答。如果兩人意見不同，雙方立場各自用自己的話寫下來，由負責那塊的人決定，結果變成一筆決定。

**為什麼是 P2**：沒有它，等待會藏在私人對話裡；但先有情境 1–3 才有東西可以問。
**獨立測試**：開一個問 Roy 的問題，確認 Roy 收到通知、回答後問題關閉並連到結果。

**驗收情境**：
1. **假設** 某件事沒有對方的答案就做不下去，**當** agent 開問題，**則** 對方收到 GitHub 通知，看板上顯示「誰在等誰」。
2. **假設** 某件事可以先做、之後再改，**則** agent 直接記成決定，不開問題（減少噪音）。
3. **假設** 對方回答了，**則** 回答的原話保留在原處，問題標成已解決；產生決定的話兩邊互相連結。
4. **假設** 兩人意見不同，**則** 雙方各自用自己的帳號寫自己的立場，沒有人能改寫對方的話。

### 情境 5：看專案進展（優先度 P2）

任何成員打開看板，就看到：每個人正在做什麼、卡在哪、在等誰；有哪些問題和任務還開著；最近的決定；做出來的成品，點一下就能打開。

**為什麼是 P2**：這是「不用開會就知道大家在做什麼」。
**獨立測試**：兩個人各做一些事之後，只看看板，回答「對方現在在做什麼、在等什麼、做出了什麼」。

**驗收情境**：
1. **假設** 成員的 agent 更新了狀態，**當** 打開看板，**則** 看到最新狀態和更新時間。
2. **假設** 有人在等別人回答，**則** 看板上看得出誰在等誰、等了多久。
3. **假設** 狀態或任務附了成品連結（PR、檔案、網址、設計稿），**則** 在看板上點得開。
4. 看板只讀資料，不在看板以外另外存一份。

### 情境 6：狀態自動更新（優先度 P2）

小婕做完一段工作，關掉 agent 之前，agent 自動更新她的狀態：剛完成什麼（附連結）、接下來做什麼、卡在哪。

**驗收情境**：
1. **假設** 使用者要結束 session，**則** agent 更新他自己的狀態，不會改到別人的。
2. **假設** 可以從 GitHub 算出來的事（合併的 PR、關掉的任務），**則** 不需要 agent 再寫一次。

### 情境 7：派任務（優先度 P3）

小婕把「做登入頁」派給 Roy。看板上 Roy 的待辦多一項；Roy 的 agent 下次開工會提到。（請 Roy 的 agent 直接執行、本人看過才跑，屬於之後的派工功能，見 Q-20261115-e7b。）

### 邊界情況

- 隊友還沒裝任何 agent：看板照樣能用；開工時提示怎麼裝。
- 離線：本機照常記錄，連上網後再同步。
- 兩個人同時改到同一個檔案：只會發生在不該發生的地方（每人只改自己的狀態檔、紀錄一筆一檔），真的發生時要能自動解決或清楚提示，不能讓使用者面對 git 衝突畫面。
- 有人手動寫了格式錯誤的紀錄：看板照樣顯示其他紀錄，並指出哪一筆有問題。
- repo 沒開 GitHub Discussions：提示一個人去開（需要管理權限），在那之前問題暫時改用 Issues。
- 非程式專案（簡報、設計、研究）：一樣能用，只要放在 GitHub repo。
- 團隊超過 5 人：不是目標，但不應該壞掉。

## 需求

### 功能需求

- **FR-001**：使用者用一個指令就能在現有 repo 開始使用 Tandem，不需要先讀文件。
- **FR-002**：開始使用時，系統在 repo 加上給 agent 的指示，**不能**覆蓋或改動既有內容。
- **FR-003**：使用者可以用 GitHub 帳號邀請隊友，並取得一個分享連結。
- **FR-004**：被邀請的人打開連結並登入 GitHub 後，系統自動接受邀請並把專案下載到本機。
- **FR-005**：系統在背景自動同步紀錄，使用者不需要執行 git 指令。
- **FR-006**：agent 開始 session 時，能取得「上次之後跟這個使用者有關的變動」，並記住已經報告過哪些。
- **FR-007**：Claude Code 和 Codex 必須能用同樣的方式使用所有功能。
- **FR-008**：決定紀錄必須有原話區：逐字原話、說話的人、出處；引用別人必須有出處連結，否則標為轉述。
- **FR-009**：決定紀錄要有強度（不能違反／傾向／直覺／只限這次）和適用範圍。
- **FR-010**：決定可以被新決定取代，舊的保留並標記，兩筆互相連結。
- **FR-011**：多人同時新增紀錄不會撞號、不會產生衝突。
- **FR-012**：agent 寫紀錄前要先給使用者確認（回條）。
- **FR-013**：需要別人回答的事，以對方會收到通知的方式提出，並在看板上顯示誰在等誰。
- **FR-014**：每個人有一份只有自己的 agent 會改的狀態。
- **FR-015**：看板顯示每個成員的狀態、等待關係、開著的問題和任務、最近的決定、成品連結。
- **FR-016**：看板可以在瀏覽器打開，不需要安裝桌面 app；介面之後要能包成桌面 app，不需重寫。
- **FR-017**：系統不經手任何 AI 服務的登入或憑證；每個人用自己的 agent 和訂閱。
- **FR-018**：系統提供檢查功能，找出格式錯誤或缺原話的紀錄。
- **FR-019**：Windows 和 macOS 都要能用。

### 主要資料

- **專案**：一個 GitHub repo。Tandem 的資料放在 repo 裡的 `tandem/` 資料夾和這個 repo 的 GitHub 討論、任務、PR。
- **成員**：有這個 repo 權限的 GitHub 帳號。
- **決定**：定案的事。有原話、決定、原因、強度、適用範圍、負責人、取代關係。
- **討論**：還沒定案、需要別人回應的事（問題、分歧）。結束時可能產生決定。
- **任務**：要派給某人做的事。結束時產生成品。
- **狀態**：一個成員現在在做什麼、卡在哪、需要別人知道什麼。
- **成品**：PR、檔案、網址、設計稿等可以點開的東西。
- **變動摘要**：某個成員上次之後，跟他有關的新決定、新討論、狀態變化。

## 成功標準

- **SC-001**：兩個人從零開始，不看任何文件，10 分鐘內都看到同一個看板。
- **SC-002**：人不需要學任何規則或格式；測試期間兩人都沒有手動執行 git 指令來同步紀錄。
- **SC-003**：開工時的變動摘要在第一個回覆出現，五行以內，Claude Code 和 Codex 都做得到。
- **SC-004**：測試期間所有決定都有原話，或明確標為轉述／無原話。
- **SC-005**：只看看板，就能正確說出對方現在在做什麼、在等什麼、做出了什麼。
- **SC-006**：兩週後兩個人還在用，而且覺得等對方的情況變少了（studio 沒過這一關）。

## 前提假設

- 使用者都有 GitHub 帳號、會基本的 GitHub 操作（D-20261115-e19）。
- 專案放在 GitHub repo；Tandem 先只支援 GitHub（D-20261115-7c2）。
- 真的要一起做事的人，電腦上已經裝好並登入 Claude Code 或 Codex。
- 團隊 2–5 人（D-20261115-a3f）。
- 使用者第一次使用時，願意在自己的 agent 裡按一次「信任這個專案」（agent 執行專案設定前的安全確認，無法跳過）。
