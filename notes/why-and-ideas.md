# Tandem 的發想和點子

這份記錄 Tandem 為什麼要做、想過哪些做法、最後選了什麼。是從 2026-11-13 到 11-16 的對話整理出來的，用整理過的文字寫，不放對話原文。

- **第一部分**：發想。痛點、想要的感覺、目標使用者。
- **第二部分**：點子和方案。想過的做法、結果和原因。

參考過的產品和研究在另一份〈研究〉（`notes/research.md`）；現在的架構、決定和待解問題在〈設計〉（`notes/design.md`）。

---

## 第一部分：發想（為什麼要做）

### 1. 起點：讓 AI 發揮真正的實力

一開始的念頭是從個人出發：AI 懂的比人多，但人不會問，它就只在淺層打轉，產出也普通。想找一套方法讓 AI 想得更深、站在前人的肩膀上，也想清楚人和 AI 各自擅長什麼、該怎麼分工。

延伸出的想法：
- 工作用的 agent 應該是**專家**，不是回答基礎問題的助手。
- 最好有一個**專家團隊**，不同觀點互相討論。
- 要能**推廣給別人用**，不只是自己客製化。
- AI 常把人的話當聖旨，矯枉過正，結果困在局部最優解，想不出更有創意的版本。

### 2. 對現在工作方式的不滿

- **開會和報告浪費時間。** 報告是 AI 做的，聽的人又把資料丟給 AI 分析，人只負責中間傳話，細節反而在傳遞中掉了；會議塞滿行程，沒辦法專心在產品上。
- **交接不確實。** 工作交給下一個人時，接手的人應該先確認懂了，這件事可以讓 AI 輔助。
- **卡在等別人同意。** 用過「改到決策就要對方同意」的流程，很煩，因為根本不清楚對方的任務，等一天進度就停一天。
- **要看的字和要做的決定太多。** 最後還是把東西貼給 AI 問，一樣繁瑣。
- **規則太多就沒人照做。** 之前那套協作流程太麻煩，一直沒真正導入，這也是決定自己做一套的原因。
- **傳統的職位劃分不適合。** 很多人是跨領域的，例如同時有設計和工程背景。

### 3. Jielle 和 Roy 的痛點

兩個人都很會用 AI、也欣賞彼此的能力，各自做都很好，但一起合作就卡卡的：試過很多溝通方式都不順，常常互相等待。各自做雖然不錯，但一個人能做到的有限；而且也猜想別人可能有一樣的困擾。

最具體的場景：各自跟自己的 AI 討論完，再用一份文件交換。很麻煩，而且想法在轉成文件的過程中會流失。

### 4. 想要的感覺

- **輕鬆**：邀請隊友就能開始，不用先建一堆規則和架構。
- **一眼看到進度**：知道專案走到哪、每個人在做什麼。
- **用最少的注意力達到最好的效果**：人只需要跟一個 agent 對接。
- **有彈性**：要讓大家都能用，就要能配合每個人自己的工作方式，不把流程寫死。

### 5. 目標使用者

- **一開始很大**：從一人團隊到整間公司。想法是兩者很像，一人團隊只是「只有老闆是人」，多人團隊是老闆底下還有 PM 和各領域的人。
- **後來收窄**：公司有現成的團隊方案可以用，所以主要對象改成像 Jielle 和 Roy 這樣的小團隊：偶爾一起做專案、參加黑客松的人。
- **暫時的假設**：大家都會用 GitHub，先不把事情弄複雜。
- **還沒回答的**：不熟 GitHub 的商業或設計背景的人怎麼上手？公司裡的法務、財務、品牌等角色放在哪？

### 6. Roy 那邊

目前沒有 Roy 自己寫的內容，以下都是間接來的：
- **他重視彈性**：整套自動化應該看情況調整，很多事交給 AI 判斷就好，就像 agent 自己決定要在主對話做還是派給子 agent。
- **他的雛形 Readback** 關注的是讓 AI 確實聽懂、不會忘。
- **他 agent 整理的文件列出的目標**：各用自己的 AI 訂閱、任何種類的專案都能用；保留原話和是誰說的；派同伴的 agent 做事要對方本人看過才執行；圖像化；同時在線和輪流做都行；能在 Windows 跑、工具不經手任何人的帳號。
- **還缺的**：他自己為什麼想做、他卡在哪，需要他補上。

### 整理時注意到的

- **範圍收窄了。** 從「讓 AI 變強、做 AI 專家團隊」縮到「兩個人合作怎麼不卡」。早期幾個不滿（AI 太聽話、會議浪費、決定太多）現在的產品還沒直接處理。
- **兩個人最大的共同痛點是「資訊在傳遞中流失」。** Jielle 這邊是交換文件時掉東西，Roy 那邊是 AI 會忘、會被摘要沖掉。這可能是 Tandem 最核心要守住的。

## 第二部分：點子和方案（想過怎麼做）

這一部分整理「要怎麼解決」：想過哪些做法、選了什麼、哪些先放著或放棄，以及原因。痛點和目標使用者見上面第一部分，參考的產品見另一份〈研究〉（`notes/research.md`），這裡只用幾個字帶過。架構細節和目前的決定清單在〈設計〉（`notes/design.md`）。

**怎麼讀**
- 每個點子寫三件事：想法是什麼、為什麼這樣想、結果。
- 結果用五種標記：**採用**、**改了**（方向保留，做法換了）、**暫緩**、**放棄**、**沒有定論**。
- 括號裡寫是誰提的：**Jielle**（@jielle2453）、**Claude**（Jielle 對話中的 AI）、**Roy**（@theroyatlas）。
- **關於 Roy**：Roy 的想法沒有一句是他本人在這些對話裡說的。只透過三個管道進來：Jielle 的轉述、Roy 的 agent 寫的情境比較文件，以及他做的東西（Readback 雛形、sudo-studio-lab 裡的 studio 流程）。下面凡是 Roy 的部分都要這樣看待。

幾個詞：**agent** 是會自己讀檔、改檔、執行指令的 AI 助手（例如 Claude Code、Codex）；**hook** 是 agent 在開工、收工等固定時間點自動執行的小程式；**MCP** 是讓 agent 主動呼叫外部工具的開放標準。

### 1. 早期的大構想（11/13 上午）

**從發想到上線的一整套工作流**（Jielle）
- 想法：設計一套涵蓋產品從發想、設計、開發到上線的流程，各職位的人和 agent 各司其職。
- 為什麼：想讓工作用的 agent 像一群專家，而且這套東西能推廣給別人用。
- 結果：**改了**。當時只把階段、職位、產品類型攤開，沒下結論。後來範圍收窄成「讓不同人的 agent 共享決定和脈絡」，完整流程沒有做。

**專家團隊，不同觀點互相討論**（Jielle）
- 想法：每個專案有一組專家 agent，從不同視角互相討論。
- 結果：**暫緩，沒有記錄**。後來被改寫成「執行依任務、審查依視角」（見第 2 節），但視角審查從來沒做。

**AI 不該把人的話當聖旨**（Jielle）
- 想法：人隨口一句修正，AI 會當成永久規則，矯枉過正，最後困在局部最優解。對策是回饋要標明強度和範圍、允許 AI 反駁、保留被放棄的方向。
- 結果：**部分採用**。決定紀錄有「強度」欄位（硬性、偏好、直覺、只限這次）。但這和 Roy 的「原話釘選、每一步都帶進去」之間有拉扯：一邊怕 AI 太死守，一邊怕 AI 忘記，兩人沒有直接談過。

**一人團隊和多人團隊是同一套架構**（Jielle）
- 想法：一人團隊就是只有老闆是人的團隊；多人團隊是老闆底下還有 PM 和各領域的人。以一個專案為單位組隊，之後再擴到一人多專案。
- 為什麼：同一套東西從一個人用到一群人，不用換工具。
- 結果：**改了**。「同一套東西」這個原則一路保留到架構討論；「職位插槽」的組隊方式後來被「決策領域和視角」取代（第 3 節）。一人多專案只在桌面版做到「多個專案切換」，跨專案的管理層沒做。

**少開會，報告和交接交給 agent**（Jielle）
- 想法：現在常是一個人用 AI 做簡報，聽的人再把資料丟給 AI 分析，人只是中間的傳輸線，細節反而掉了。改成共享原始資料、由讀的人自己問，人只補上「只有他能給的判斷」。
- 結果：**採用（換了形式）**。這成了 Tandem 的核心精神：決定連同原話記下來，對方開工時 agent 主動報告「跟你有關的變動」，不用寫報告。

**交接時雙方都要先確認**（Jielle）
- 想法：交出方先確認、接手方先弄懂狀況，中間由 AI 輔助。
- 結果：**暫緩，沒有記錄**。Claude 畫過交接流程（交接包附決策原因、未解問題才找人、接手方確認理解）；Roy 的 Readback 有更強的「交棒驗證」（接手的模型要先答對情境題）。兩人其實都想要，但 001～003 都沒做，003 的規格明寫不在範圍。

**人像顧問，有不確定的事才找人**（Jielle）：**採用（縮小版）**，變成「只有需要對方回答才做得下去的事，才開問題給他」（`tandem ask`），其他先做、先記。

### 2. 團隊 agent 長什麼樣（11/13）

**團隊層和 AI 引擎分開**（Claude）
- 想法：「團隊 agent」不是某一個模型，而是存放決定、規則、事件的一層；Claude、Codex 只是被接進來做事、隨時可換的引擎。
- 為什麼：換模型不會失憶，不同人可以用不同 agent，不被單一廠商綁住。
- 結果：**採用**。現在的紀錄放在 repo，任何 agent 都能讀寫。

**大腦和雙手；團隊大腦放雲端能不能用訂閱**（Jielle 問，Claude 整理）
- 想法：Jielle 原本理解成一條直線：個人 agent → 團隊狀態 → 團隊 agent → 再傳回來。Claude 修正成「以團隊狀態為中心的星狀」，並分成負責思考的「大腦」和負責動手的「雙手」。
- 雙手的三種做法：A. 成員的 agent 用自己的訂閱認領任務；B. 雲端用 API 付費；C. 交給官方雲端功能（例如 GitHub Actions）。當時建議早期用 A。
- Jielle 追問一人團隊會不會因此又回到「各自管 agent」：答案是不會，因為狀態屬於團隊，agent 只是領任務的工人。Claude 也因此提過「先做成 Claude Code plugin」。
- 結果：**改了**。plugin 優先後來被「開放標準、兩家平等」取代（第 4 節）。訂閱規則前後查了好幾次，結論一再修正，最後決定「認證方式不能寫死」。

**個人助理加派去團隊的工人**（Jielle）
- 想法：每人有一個自己用的助理 agent，另一個借給團隊當工人。大腦一直在雲端，誰今天在線上，就由誰的電腦出力；人只提供算力，不用管理。
- 為什麼：不管有多少人在線，團隊都能運作。
- 結果：**暫緩**。設計上補了邊界（可用時段、用量上限、能動哪些 repo、哪些動作要核准），也談到別人派的任務在你電腦上跑的安全問題。後來跟 Roy 的「本人看過才跑」衝突，背景工人一直沒做。

**agent 依人、依專業、依階段還是依任務劃分**（Jielle 問）
- 想法：Claude 的結論是：人只用來分配算力和額度；執行依任務，一個任務一個 agent；審查依視角，各自在全新的上下文裡看；階段只是專案狀態。一句話概括為「agent 是函式，不是員工」。
- 為什麼：Jielle 本來就不認同傳統職位劃分；把 agent 照職位拆開，等於把人的限制複製到 AI 身上。
- 結果：**只停在原則**。寫進了設計總覽，沒有對應的功能。

**個人 agent、專案 agent、團隊大腦怎麼分工**（Jielle）
- 想法：Jielle 原本的構想是每人有個人 agent 和專案 agent，團隊再有一個大腦統整大家的專案 agent。比較了三種：A. Jielle 的原構想；B. 每個專案一個大家共用的 agent；C. 混合：專案的事實只放在大腦，人只對接自己的個人 agent。
- 為什麼選 C：A 要大腦統整好幾份各自的版本，又回到「AI 摘要給另一個 AI」的傳話問題；B 要人同時對接好幾個 agent。判斷原則是「事實只存一個地方、人只對接一個 agent」。
- 相關：Jielle 也提出「每件事先經過助理 agent，專案之間資料要隔離」，這被併進 C。
- 結果：**改了**。原則保留；實作上，「大腦」變成 GitHub repo 加 Discussions，「個人 agent」就是每人自己的 Claude Code 或 Codex，透過 hook 讀寫。

**公司其他部門放哪**（Jielle 問）
- 想法：法務、品牌、財務不參與開發，但會影響專案。提過規範由上往下繼承、部門窗口 agent、跨專案的組合層。
- 結果：**放棄**。原本是預留、第一版不做；目標使用者改成小團隊後，這一層從路線圖拿掉。

**哪些要送進團隊，哪些留在個人**（Jielle 問）
- 想法：判斷標準是「這件事有沒有改變大家共享的現實」。決定、問題、承諾要送；思考過程、草稿、閒聊不送。送之前先給本人確認，原始對話永遠不集中存放。
- 結果：**採用**。現在記決定前，agent 會先列出草稿讓本人確認；對話本身不會同步給對方。

### 3. 人怎麼參與、誰能決定（11/13 下午）

**衝突是好事**（Jielle）
- 想法：兩人的指令衝突，代表 agent 沒有盲從，也正是需要人來判斷的地方；有時兩邊都對，只是情境不同。
- Claude 補充：分歧分四種（事實、情境不同、價值取捨、不確定），各有處理方式，整理成「分歧卡」交給人，agent 只整理不裁決。
- 結果：**部分做**。`tandem disagree` 會開一則討論、記下立場，但沒有分歧核心、成立條件、可能方案這些欄位。

**不按職位分工**（Jielle）
- 想法：Jielle 是設計加工程的跨領域背景，不認同傳統職位；設計的本質是在使用者、工程、行銷等視角之間找平衡。
- Claude 據此把「職位」拆成三樣：要被考慮的**視角**、誰拍板的**決策領域**、實際會做的**能力**。沒人帶的視角由 agent 補上。
- 結果：**改了**。後來「流程不寫死」讓這套結構變薄，現在只有 `team.md` 讓團隊用白話寫自己的習慣。

**大家都能丟想法，但不是大家都能拍板**（Jielle）
- 想法：分成三種權利：所有人都能提出、相關視角的人要被諮詢、負責人拍板；決定後要讓提出想法的人知道結果。
- 結果：**沒有做成機制**，被「流程不寫死」取代。

**白板：放還沒定的想法**（Jielle）
- 想法：一個低承諾的地方，想法可以隨手丟，不用任何人同意、不發通知；確定要做才進入設計和執行。想法依「想法 → 探索中 → 提案 → 已決定」推進，很久沒人碰就自動封存。
- 結果：**暫緩**。一直沒做。後來 Jielle 問是不是被 Discussions 取代了，答案是沒有；Claude 建議放進 Discussions 的 Ideas 分類，由團隊大腦自動封存，於是跟著團隊大腦一起停住。

**誰可以自己決定、誰要同意**（Jielle 問，Claude 提出等級）
- 想法：Jielle 用過「改到決策就要對方同意」的流程，覺得很煩。Claude 提了 L0～L4 五個等級（agent 自己決定 → 全體決定），依可逆性、影響誰、成本、有無前例判斷；只找真正被影響的人，請求要附「對你的影響」；負責人用認領加確認產生；負責人不必是專家，沒有專家的領域一樣能拍板，只是要更保守、更常檢討。
- 結果：**放棄**等級制度，改成決定紀錄的強度欄位，加上交給 AI 判斷。「意見不同時誰決定」至今還是開放問題，等 Roy 一起決定。

**不想等 24 小時：先交給對方的助理 agent 審**（Jielle）
- 想法：與其等對方本人，不如送到對方的助理 agent，沒問題就通過，有問題兩邊 agent 先談，談不攏才找人。Claude 補上「樂觀執行」：可逆的部分照常往下做，只有不可逆的那一步才等。
- 結果：樂觀執行**部分採用**：skill 教 agent 能先做就先記決定；紀錄直接推到 main 不開 PR；程式碼的 PR 也可以自己合併，不等對方。代理人審查**沒做，也沒記錄為什麼放下**。

**每次載入的內容越少越好**（Jielle 問）
- 想法：分清楚每一輪都會載入的、開工時載入的、用到才載入的，常駐的東西要說得出值得的理由。
- 結果：**採用**。給 agent 的規則區塊很短，詳細做法放在用到才讀的 skill，開工報告限五行。不過後來發現同一段說明散在五個地方，還沒整理。

**用模擬使用者補上使用者視角**（Jielle 問）：把 MatrAIx 包成可開關的模組，做第一輪篩選。**暫緩，沒有記錄**。

### 4. 怎麼接上 agent（11/13 下午到晚上）

**MCP、SDK 還是協定**（Jielle 問）
- 想法：兩個方向相反。MCP 是 agent 主動呼叫我們；SDK 和協定是我們去驅動 agent（啟動、看每一步、中途叫停）。Claude 建議先做 MCP 加 hook，之後再加驅動；最完整的版本兩個方向都要。
- 結果：**採用**這個區分，但順序後來變了（見下面「實際做的時候」）。

**把 GitHub 放進架構，第一版不架伺服器**（Jielle 問，Claude 提）
- 想法：決定、白板、對照表放 repo 裡的 Markdown；任務和分歧卡用 Issues；團隊大腦用 GitHub Actions 觸發；被影響的人在 PR 上被標記。這一版連 MCP 和 SDK 都先延後。
- 結果：**採用**「只用 GitHub、不架伺服器」。團隊大腦用 Actions 這部分沒做。

**同時支援 Claude Code 和 Codex，而且要正式**（Jielle）
- 想法：Claude 先提了一個命令列核心加兩份薄設定；Jielle 覺得這像以 Claude 為底再轉接 Codex，要求更正式的做法。改成：核心不屬於任何一家，透過開放標準（AGENTS.md、Agent Skills、MCP）接入；寫一份有版本號的協定規格；hook 降為選用；不能違反的規則交給 GitHub；用相容性測試定義什麼叫「支援」。
- 結果：**採用方向，做法打了折**。兩家都讀同一份 AGENTS.md、同一套 skill 和 MCP。但規格沒寫成獨立文件，hook 反而成了主要的串接方式，GitHub 強制規則在免費方案的私人 repo 上也用不了。

**團隊大腦怎麼派工：三種執行器**（Jielle 問）
- 想法：大腦把任務寫成 issue，交給執行器，一律用 PR 交回。執行器有三種：A. GitHub Actions（雲端、API 付費）；B. 成員電腦上的背景工人；C. 人在自己的 agent 裡認領。Jielle 再問 B 和 C 差在哪、要不要人管：結論是兩者是同一個人的兩種模式，差在你在不在場；B 可以用排程、定期檢查或事件觸發。
- 結果：**暫緩**。001 只有 `tandem task` 開 issue 指派人，不能選執行器。派工要等 Roy 一起決定「別人派的事要不要本人看過才跑」。

**最完整的版本**（Jielle 要求）
- 想法：九層的完整版：多了雲端常駐大腦、可插話的控制協定、模擬使用者、其他平台的雲端 agent、公司層、治理與稽核。整理成「產品設計與功能總覽」，共 16 項功能，其中 9 項列為第一版。
- 結果：**改了**。這份總覽後來被範圍收窄（第 5 節），但它一直是 Jielle 對照「有沒有照設計做」的基準。

**這算 LangChain 嗎**（Jielle 問）：不算，我們是協調現成的 agent，不是自己組 agent。只**借概念**（通知／提問／審查三種打擾方式、收件匣、等人時暫停再接續）。

**實際做的時候發生了什麼**
- 001 只做了命令列工具加 hook。MCP 伺服器、相容性測試、團隊大腦都被 Claude 自行延後，沒有先問 Jielle。Jielle 後來發現，於是在 003 補回 MCP（8 個工具）。
- 相容性測試在 003 列了 12 個情境，Codex 那半交給 Roy 在他電腦上測，目前還沒測。

### 5. 收斂：範圍和做法（11/14～11/15 上午）

**以 Readback 為基礎改，還是重寫**（Jielle 問）
- 結果：**重寫**。兩者解決的問題和時間尺度不同（Readback 是幾分鐘內多人指揮同一個 agent），而且 Readback 沒有授權條款。它的回條、原話釘選、成品檢查、交棒驗證當設計參考，之後也可能當模組。目前只做到「原話」的一半。

**Roy 的文件帶來的方向**（Roy，來自他的 agent 寫的文件）
- 內容：他的目標包括本人看過才跑、任何專案都能用（不限寫程式）、要能一眼看出誰在等誰、Windows 上的安全；並提出三條路：直接用現成的、在現成工具上加功能、自己做。
- 結果：三條路**沒有定論**。當時判斷比較接近「在現成工具上加功能」，實際上越做越接近自己做，但沒有記成決定。他問的四個問題也沒有正式回覆。

**一起用同一個 agent：會議模式到房間**（Jielle）
- 想法：學 Omnigent，開會時大家一起跟同一個 agent 講；希望大家都能在 session 裡輸入。
- 過程：agent 不進 Google Meet（開發介面只有測試版，而且已宣布關閉），改成房間獨立存在，沒開會也能用；最快的做法是 Claude Code 的 Discord channels，但只支援 Claude；另一個選擇是用 GitHub 討論串當房間。
- 結果：**採用**，記成〈共用房間〉的決定。後續演變見第 6 節。

**不熟 GitHub 的人怎麼上手**（Jielle 問）
- 想法：分訪客、成員、開發者三層，git 操作全交給 agent，介面不出現 GitHub 術語。
- 結果：**暫緩**。記成〈先假設使用者都會用 GitHub〉。Discord、Slack 也延後，記成〈先只做我們自己的系統加上 GitHub〉。

**流程不寫死**（Roy 的想法，經 Jielle 轉述；Jielle 也同意）
- 想法：自動化要依情境調整，很多事交給 AI 判斷，就像 agent 自己決定要在主對話做還是派出去。Claude 補上配套：格式和存放位置固定，其他交給 AI；AI 的判斷要讓人看得到、可以糾正，糾正過的會記住。
- 結果：**採用**，記成〈流程不寫死〉。這也是 L0～L4、參與權利這些制度被拿掉的主要原因。

**做一件小事，還是一整套工作流**（Jielle）
- 想法：Jielle 先提出兩條路：讓產品能配合每個人的工作方式，或專心做好一件小事。Claude 建議不要做 T3 Code 那種讓各家 agent 互通的層（太擠），只做「讓每個人的 agent 共享決定和脈絡」。Jielle 擔心只做一小塊，使用者又要在各產品之間拼湊。
- 折衷：核心很小，但由我們負責整套預設流程和各工具之間的串接；指標是人在工具之間手動搬資料的次數，目標是零。
- 結果：**採用**，記成〈核心只做一件事〉。紀錄裡註明這個折衷是 Claude 提的。

**用 Tandem 開發 Tandem，先從紙本版開始**（Jielle 問，Claude 提紙本版）
- 想法：還沒寫程式就先用 Markdown 格式加 AGENTS.md 開始用，哪裡麻煩再寫成工具。
- 結果：「用自己開發自己」**採用**；「先紙本版、不寫程式」被後來的〈直接做完整版〉**取代**。

**開發紀錄要不要公開**（Jielle 問）：比較了一開始就公開、產品和紀錄分兩個 repo（Claude 建議）、先全私人三種。Jielle 選**先只開一個私人 repo**，要公開時再搬。

**從第 0 步到完整版的路線**（Jielle 要求）
- 想法：紙本版 → 核心工具 → GitHub 串接 → 預設工作流 → 房間 → 派工 → 完整版，每一步有通過條件；最底下的紀錄格式從第 0 步定好就不重寫。
- 結果：**改了**。實際照 001 核心、002 桌面版、003 在 app 裡用 AI 的順序走，房間提前做了。

**要有介面，還要能點到成品**（Jielle）
- 想法：要能看到對方的進度、專案狀態、待辦，而且點得到成品。為此新增每人一份的狀態檔。
- 結果：**採用**，記成〈要做一個介面〉。

**命名**（Jielle）
- 想法：Claude 先給 Baton、Commonplace 等候選；Jielle 想用 Nexus，但撞名嚴重，還有兩個定位幾乎一樣的專案；Jielle 再提 Tandem 和「乘法」方向，乘法對應的英文字太常見。
- 結果：**Tandem 當代號**，正式名稱還在 Discussions 等 Roy。

**建在 sudo-studio-lab，但不沿用 studio 的規則**（Jielle；Roy 的 studio 是重要背景）
- 想法：Roy 已經在組織裡做了一套 studio 流程（規則只寫在 AGENTS.md、進度檔、決定紀錄、PR 交接區塊），跟我們的設計很像。Claude 原本建議沿用並擴充。
- 結果：Jielle 說兩人覺得 studio 太麻煩、根本沒導入，所以**不沿用，從頭設計更輕的版本**。這個「規則太多沒人照做」的教訓，直接變成後面最重要的標準。

**資料怎麼分層**（Jielle 要求再想一次）
- 想法：檔案不會通知人，多人改同一個檔案會衝突，而且別人的原話可以被亂寫。改成：定案的決定放檔案；要討論的（問題、分歧）放 GitHub Discussions；要派的任務放 Issues；引用別人的話要附連結。Jielle 擔心 issue 太亂、也分不清哪些是過渡期的決定，於是改成「先定完整版的樣子，雛形只是最輕的骨架」。
- 結果：**採用**。

**先驗證一週，還是直接做完整版**（Claude 建議前者，Jielle 選後者）
- 想法：Claude 建議先各寫幾次真實卡住的經驗、檢討 studio 為什麼沒用起來、用紙本版跑一週再寫規格，避免閉門造車。
- Jielle 的判斷：該講的想法都講了，現在回答驗證問題價值不大，做出來再看哪裡不順。同時講出最重要的標準：要輕鬆，邀請就能開始，不用先建規則。
- 結果：記成〈直接做完整版再調整〉和〈最重要的標準是輕鬆〉（強度：硬性）。紀錄裡也保留了 Claude 的反對理由，萬一做出來沒人用可以回頭對照。

**桌面版加分享連結；網頁版還是桌面版**（Jielle）
- 想法：下載桌面版、用分享連結邀隊友就能開始。研究 T3 Code 後改成「一個本機核心，搭配可以放到任何地方的網頁介面」：先本機網頁，再包成桌面版，雲端網頁版之後再說。
- 結果：記成〈學 T3 Code：本機核心加網頁介面〉。「點連結不用輸入帳號就加入」需要一個小後端，**暫緩**；雲端網頁版**暫緩**。

**照搬驗證過的做法**（Jielle）：**採用**，之後每份規格都標明參考來源。

### 6. 做出來之後的轉折（11/15 下午到晚上）

**001 → 002：還是太麻煩**（Jielle）
- 想法：001 做完後，Jielle 覺得看不出效果、太麻煩，自己不會想用，Roy 應該也不會，所以先把完整度做高，也不用等 Roy 測。Claude 想把「先做 002」記成決定，Jielle 說不用記。

- 結果：**採用**，0.2.x 已發行。程式簽章**暫緩**，兩人先關掉 Windows 的 Smart App Control。

**002 → 003：在 app 裡用自己的 AI，不要跳終端機**（Jielle）
- 想法：像 T3 Code 一樣，在 app 裡登入自己的訂閱，可以登好幾家，同一個對話框選要用哪一家。
- 選項：Claude 這邊有三條路：A. 把原版 Claude Code 嵌成終端機面板；B. 對話框配 API key；C. 對話框配訂閱（T3 Code 的做法，透過 Agent SDK）。Jielle 要訂閱和 API key 都能用。重讀條款後：執行使用者自己裝的原版 Claude Code、用它自己的登入流程，是允許的；Agent SDK 配訂閱則不行。Jielle 問過要不要乾脆縮成只給自己用的小專案，結論是不用。
- 結果：記成〈先補 agent〉。Tandem 在背景執行原版 `claude` 程式，Codex 用官方的 app-server 介面，Tandem 不經手任何 AI 帳號憑證。

**「沒照我原本的設計做嗎？」**（Jielle）
- 想法：對照設計總覽後，真正偏離又沒先問的有四項：MCP、相容性測試、hook 從選用變主要、引擎轉接只做到開終端機。其他沒做的，多半是後來的決定刻意拿掉的。
- 結果：Jielle 決定慢慢補回三件事：app 裡的 AI、團隊大腦（資料與派工）、房間。順序上先補 agent，其餘照原本的規格往後排。

**對話權限模式**（Jielle 覺得體驗不好）
- 想法：T3 Code 預設什麼都不問，我們每件事都問。提議三種模式（完全授權、自動接受修改、需要核准），預設自動接受修改，只讀的指令都不問。
- 結果：**沒有定論**。草稿擬了，但沒有寫入紀錄。

**團隊大腦真的需要嗎**（Jielle）
- 想法：Jielle 問大腦是不是要幫大家派工、這樣會不會比各自用自己的 agent 好。Claude 先澄清大腦原本就不負責派工，接著建議整個拿掉：衝突提示在記決定時當場做，「放太久沒回」用一般程式標紅就好，不需要另一個 agent 和團隊 API 費用。
- 結果：**暫緩，沒有記錄**。Jielle 沒有正式回覆，那筆草稿也沒寫入。

**我們的價值是什麼，不就是 GitHub 嗎**（Jielle）
- 想法：存資料的地方確實就是 GitHub。Claude 的回答是：agent 不會自己去讀 GitHub；一串討論不等於一個決定；很多決定發生在人跟 agent 的對話裡，GitHub 根本收不到。所以價值在於：不用任何人整理，每個人的 AI 開工時就知道團隊定了什麼。
- 結果：**沒有定論**。Claude 也承認這個價值還沒被證明、核心很小。建議兩週後一起檢查還有沒有在傳長文件。

**房間的最後樣子**（Jielle）
- 演變：先擔心「大家共用主持人的訂閱」違反條款，列過三種做法：每個人帶自己的 agent 進房間、團隊出一把 API key、別人的話由主持人按送出。後來更正為條款沒寫清楚，是灰色地帶，又提議做成三種模式可選。
- Jielle 的決定：房間背後是一則 GitHub Discussion；大家打的字直接送進主持人的 AI；AI 可以做事，但改檔案、跑指令要主持人核准；隨時能整理筆記，結束時整理並關閉討論。
- 結果：**採用（暫定）**，記成〈房間〉的設計決定，強度是「直覺」，等 Roy 一起決定。注意這和早期「房間只討論、不執行」的方向不同。

**發行流程簡化**（Jielle）
- 想法：打包前一定先重建全部（修掉 0.2.0 包到舊版的問題），一個指令發版。Claude 本來建議先不用 GitHub Actions 打包，理由是還沒有外部使用者、總時間未必比較短；Jielle 還是要用。
- 結果：**採用**。第一次在 GitHub 上打包只花約三分半，比在自己電腦上快很多。

**整理架構**（Jielle 要求先只討論）
- 想法：同一個動作在三個入口各寫一次、給 agent 的說明散在五處、兩種儲存的分界沒寫下來等六項。
- 結果：**沒有動手**。Jielle 決定先回頭整理痛點和整份設計，也就是這份文件的由來。
